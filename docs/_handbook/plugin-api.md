# Plugin API reference

Generated by `scripts/gen_plugin_api.py` from SDK 4.0.0. Do not edit.

Signatures, and each docstring collapsed to one paragraph.
Within this major, existing keys do not gain methods;
a new capability is a new key or a new event.

## Kernel

#### `shiori_sdk.runtime.PluginRuntimeContext`

What a plugin's ``setup(ctx)`` receives. ``provide`` / ``require`` / ``get`` take service keys declared in manifest ``provides`` / ``inject`` / ``optional_inject``; ``on`` / ``watch`` / ``emit`` join the generation's event chain. ``effect`` takes a label the host records with the disposer. Plugin tasks and reload draining are services, not context members: ``BACKGROUND.spawn`` and ``RUNTIME.on_drain`` (``shiori_sdk.core.services``).

- `plugin_id: str`
- `plugin_dir: pathlib.Path`
- `expose(api: object) -> None`
- `effect(label: str, dispose: Dispose) -> None`
- `provide[T](key: kernel.contracts.Key[T], impl: T) -> None`

  Publishes ``impl`` under a key declared in manifest ``provides``.

- `require[T](key: kernel.contracts.Key[T]) -> T`

  The current provider of a key declared in manifest ``inject``.

- `get[T](key: kernel.contracts.Key[T]) -> Optional[T]`

  The current provider of a key declared in ``optional_inject``, or None.

- `on[E](event_type: type[E], handler: OnHandler[E]) -> None`

  Joins the ordered chain; return the (replaced) event or ``Veto``.

- `watch[E](event_type: type[E], handler: WatchHandler[E]) -> None`

  Listens read-only to the final event, serially, without delaying emit.

- `async emit[E](event: E) -> Union[E, kernel.contracts.Veto]`

  Emits through the kernel: ``on`` chain, core checks, then watchers.

#### `shiori_sdk.runtime.HostServiceUnavailable`

The manifest asked for a service the host did not assemble. Raised while building that plugin's setup context, and the message names the missing service. Deliberately not an ``AttributeError`` so ``getattr`` defaults can never swallow it.

#### `shiori_sdk.kernel.contracts.Key`

Typed identity of a provided service; ``name`` equals the manifest string.

#### `shiori_sdk.kernel.diagnostics.PluginDiagnostic`

Stable host-facing failure details; ``reason`` preserves the original cause. ``stage`` names where the failure happened (``validation``, ``discovery``, ``trust``, ``dependency``, ``setup``, ``reload`` or a renderer entry kind) and ``state`` the lifecycle state the plugin is left in.

- `code: str`
- `stage: str`
- `field: str`
- `reason: str`
- `path: str`
- `state: str`

- `to_dict() -> dict[str, str]`

  Return JSON-compatible diagnostic fields for bridge/installer callers.

#### `shiori_sdk.kernel.contracts.Veto`

Returned by an ``on`` handler (or a core check) to reject the event.

- `reason: str`

#### `shiori_sdk.kernel.contracts.PluginStarted`

A plugin's setup finished; it is ACTIVE.

- `plugin_id: str`

#### `shiori_sdk.kernel.contracts.PluginFailed`

A plugin did not start: setup failed (FAILED) or it could not run (BLOCKED).

- `plugin_id: str`
- `diagnostic: kernel.diagnostics.PluginDiagnostic`

#### `shiori_sdk.kernel.contracts.PluginStopped`

A plugin's scope was released (stop, reload or host unload).

- `plugin_id: str`

## `shiori_sdk.core.conversation`

Turn events, ``COMMANDS``, and the initiated-delivery socket (D19, #902). The host emits one event per turn stage through the plugin kernel: ``on`` handlers run in plugin order and may return a replaced event, the core's fixed checks run on the final one, then ``watch`` handlers see it. Every event is a frozen projection of the host's turn state, never the state itself: the host applies only the fields documented as *writable* back to the turn and ignores changes to the others. Container fields are tuples, frozensets or read-only mappings. ``Veto`` stops a stage where it can stop: it aborts the turn with ``Veto.reason`` as the reply (``TurnStarting``, ``ReasoningStarting``) or ends the tool loop with it (``StepStarting``). The other events cannot be vetoed; a veto there fails the turn. A vetoed event reaches no watcher.

### `commands`

Target `shiori_sdk.core.conversation.Commands`.

#### `shiori_sdk.core.conversation.Commands`

Bot commands, answered right after the session is acquired. A message whose head is ``/name`` (any case, an ``@bot`` suffix and arguments allowed, see ``shiori_sdk.commands.command_name``) is answered by the handler registered under ``name``, ahead of the memory backlog guard; a command turn retrieves no memory and calls no model. Other messages, and commands nobody registered, are ordinary turns.

- `register(name: str, handler: CommandHandler, *, description: str | None = None) -> Callable[[], None]`

  Answers ``/name`` with ``handler`` and returns the registration's removal. ``name`` is lowercase, without the leading slash, whitespace or ``@``; a name already registered raises ``ValueError``. ``description`` puts the command in the command menu channels show; an alias leaves it None. Hand the removal to ``ctx.effect`` so unloading the plugin removes the command.

### `conversation`

Target `shiori_sdk.core.conversation.Conversation`.

#### `shiori_sdk.core.conversation.Conversation`

Deliver a reply the host initiated, outside a user turn. The host provides this key for the generation it belongs to. 4.x cannot add methods to this protocol later (D19).

- `async deliver_initiated_reply(reply: core.conversation.InitiatedReply) -> core.conversation.InitiatedDelivery`

  Send ``reply``, store what was sent, and emit ``InitiatedMessageCommitted``. Returns what was stored (see ``InitiatedDelivery``). Raises before sending anything when the session is not a role session, the role is gone, the reply fails validation against ``reply.moods``, natural chat is off for a multi-message reply, tool facts arrive without that sequence, or a single reply is stale (``expected_mood_updated_at``). Raises when a send fails or is refused mid-way. A single reply then stores nothing. A sequence keeps the prefix already sent (stored and announced), and the first message of a refused desktop sequence raises instead of returning an empty result. Account sends that fail or whose outcome is unknown stay on the session as delivery records marked ``failed`` / ``uncertain``, outside the conversation history. A sequence needs a runtime lease or an already bound channel-sequence owner.

#### `shiori_sdk.core.conversation.ConversationMessage`

One message of a turn's history window.

- `role: str`
- `content: str`
- `tools_used: tuple[str, ...]`

#### `shiori_sdk.core.conversation.InitiatedDelivery`

What one initiated delivery stored. ``message_ids`` are the committed messages, in order. ``complete`` is True only when every message of the reply was sent and stored. An incomplete result is not an error. For a single reply it means the transport refused it (for instance a desktop chat that is not the role's own) and nothing was stored. For a sequence it means a newer user message in that chat, the role's removal or natural chat being switched off stopped it: the prefix already sent is stored and announced (possibly none), the rest is dropped.

- `message_ids: tuple[str, ...]`
- `complete: bool`

#### `shiori_sdk.core.conversation.InitiatedMessageCommitted`

A role message the user did not ask for was stored on the role session. The host emits this after the message is committed, so ``message_id`` names a stored message. Two publishers emit it: - initiated delivery (``CONVERSATION`` / ``PROACTIVE_HOST.deliver``, and the host's own proactive loop until it moves into the plugin), once per delivered reply. A natural sequence emits once for the delivered messages: ``message_id`` is the last one and ``assistant_response`` their texts joined by a blank line. ``tools_used`` is ``("message_push",)``. - a host-owned push (the ``account_send`` tool reaching an external chat outside a live turn), once per push. ``tools_used`` names the tool. ``thread_id`` is the conversation thread the message belongs to; a role's session mixes threads, so subscribers read history with it. ``source`` names who started the message: the ``InitiatedReply.source`` a plugin passed (by convention its plugin id; the host's proactive loop and Drift use ``"proactive"``), or ``"push"`` for a host-owned push. Plugins watch it; they do not construct it.

- `session_key: str`
- `channel: str`
- `role_id: str`
- `thread_id: str`
- `source: str`
- `chat_id: str`
- `assistant_response: str`
- `tools_used: tuple[str, ...]`
- `message_id: str`

#### `shiori_sdk.core.conversation.InitiatedReply`

One initiated reply, including its target, media and natural sequence. The reply speaks for the role that owns ``session_key``, which must be a role session (``role:<role_id>``); any other key raises ``ValueError``. The target must be one that role can reach: its own desktop chat (``channel="desktop"``, ``chat_id="role:<role_id>"``), a private chat with the bound user through one of its online accounts, or an ``account_target`` sent through the role's account on ``account_channel``. Both account fields are given together or not at all. With an account target, ``channel`` / ``chat_id`` name the chat the reply is recorded under; a sequence first opens there, so for a sequence they must also be a chat the role can reach. ``expected_mood_updated_at`` and ``moods`` are the ``PROACTIVE_HOST.reply_state(role_id)`` the caller read when its work started. The mood and thought are validated against ``moods``. When the role's stored mood changed after that read (a passive reply landed in between) the reply is stale: a single reply raises without sending; a sequence is still sent and stored, but its mood and thought do not replace the newer state. ``content`` is the text stored on the role session. When ``messages`` is non-empty it must equal those texts joined by a blank line, and natural chat must be on for the role; delivery then sends each text as its own message and stores them in order. Media rides on the first message. ``tool_facts`` ride along with ``messages`` only. The stored messages are marked ``proactive`` with source ``proactive`` and ``tools_used=["message_push"]`` whatever ``source`` says; ``source`` only reaches ``InitiatedMessageCommitted``. They carry no evidence item ids.

- `session_key: str`
- `content: str`
- `source: str`
- `channel: str`
- `chat_id: str`
- `mood: str`
- `thought: str`
- `expected_mood_updated_at: str`
- `moods: tuple[str, ...]`
- `media: tuple[str, ...]`
- `messages: tuple[str, ...]`
- `account_channel: str`
- `account_target: accounts.targets.AccountTarget | None`
- `tool_facts: tuple[core.conversation.InitiatedToolFact, ...]`

## `shiori_sdk.core.crash_reporting`

``CRASH_REPORTING``: the core service arbitrating process-wide crash hooks (D13b). ``sys.excepthook``, ``threading.excepthook`` and an event loop's exception handler are process globals. Collectors register through this one service instead of rewriting them directly, so overlapping plugin generations hand the hooks over in order and the last one out restores the originals. ``session_key`` and ``top_frame`` are part of the same protocol (maintainer, 2026-10-27). The collector attributes a crash after it injects this key; they are not a second key, and the ``diagnostics`` capability is gone.

### `crash_reporting`

Target `shiori_sdk.core.crash_reporting.CrashReporting`.

#### `shiori_sdk.core.crash_reporting.CrashReporting`

Installs one active crash collector at a time, stacked by ``owner``.

- `install(owner: object, handler: logging.Handler, system: Callable[[type[BaseException], BaseException, traceback | None], object], thread: Callable[[_thread._ExceptHookArgs], object], loop: asyncio.events.AbstractEventLoop | None, loop_handler: Callable[[asyncio.events.AbstractEventLoop, dict[str, object]], object]) -> tuple[Callable[[type[BaseException], BaseException, traceback | None], object] | None, Callable[[_thread._ExceptHookArgs], object] | None, Callable[[asyncio.events.AbstractEventLoop, dict[str, object]], object] | None]`

  Makes ``owner`` the active collector; returns the original hooks. The originals are the hooks in place before any collector, so the collector can chain to them.

- `uninstall(owner: object) -> None`

  Retires ``owner``; the previous collector or the originals take over.

- `session_key() -> str | None`

  The host's current passive-turn attribution, if a turn is in progress.

- `top_frame(tb: traceback | None) -> str`

  The first frame the host or a plugin owns, else the innermost filename.

## `shiori_sdk.core.markdown_memory`

``MARKDOWN_MEMORY``: a role's Markdown memory documents on the host (#907 P6b). Each role keeps ``MEMORY.md`` (long-term memory), ``SELF.md`` (the role's self-understanding), ``PENDING.md`` (facts waiting to be merged into ``MEMORY.md``) and ``HISTORY.md`` (an append-only archive) under its role directory. The files, their schema and their locations stay with the host; this port reads and rewrites them. The host provides this key before any plugin starts. The port also keeps a role's memory state: plugin-owned values stored in the role record next to the host's own initialization state. They survive restarts and are deleted with the role. The port does not belong to a generation; a process-level plugin resource can keep one reference across runtime reloads.

### `markdown_memory`

Target `shiori_sdk.core.markdown_memory.MarkdownMemory`.

#### `shiori_sdk.core.markdown_memory.MarkdownMemory`

Markdown memory of every role on the host.

- `default_self: str`

  The ``SELF.md`` template a role starts from.

- `role(role_id: str) -> core.markdown_memory.RoleMarkdownMemory | None`

  The role's documents, or ``None`` when the role does not exist.

#### `shiori_sdk.core.markdown_memory.RoleMarkdownMemory`

One role's Markdown memory documents and memory state. Merging ``PENDING.md`` into ``MEMORY.md`` is two-phase. ``snapshot_pending`` moves the pending facts aside, so facts appended while the merge runs go to a new ``PENDING.md``. The merge then ends with ``commit_long_term`` (facts are merged) or ``rollback_pending_snapshot`` (the facts go back). A snapshot left by a process that exited mid-merge goes back on the next ``snapshot_pending``.

- `read_long_term() -> str`

  ``MEMORY.md`` as stored; empty when the document is missing.

- `read_self() -> str`

  ``SELF.md`` as stored; empty when the document is missing.

- `write_self(content: str) -> None`

  Replaces ``SELF.md``; the host normalises it to the document schema.

- `self_seed_pending() -> bool`

  Whether ``SELF.md`` still waits for its first generated version. True while the document is a default template the host will replace with a version generated from the role's settings. Rewriting ``SELF.md`` then would read as a user edit and stop that generation.

- `snapshot_pending() -> str`

  Moves ``PENDING.md`` aside and returns its facts. Returns an empty string, and moves nothing, when no fact is pending.

- `commit_long_term(content: str, *, history_entry: str) -> None`

  Replaces ``MEMORY.md`` with ``content`` and drops the pending snapshot. A non-empty ``MEMORY.md`` is first copied to ``MEMORY.bak.md``. ``content`` is normalised to the document schema. A non-empty ``history_entry`` is appended to ``HISTORY.md`` as it is.

- `rollback_pending_snapshot() -> None`

  Puts the snapshot's facts back before ones appended since; no-op without one.

- `read_state() -> Mapping[str, object]`

  A copy of the plugin-owned memory state; empty once the role is deleted. The host's own initialization keys in the same record are left out.

- `read_recent_context() -> str`

  The visible ``RECENT_CONTEXT.md`` body. Empty when the document is missing, unstamped, or no longer visible to the role's current threads. The host does not recreate a deleted role's memory directory.

- `write_state(key: str, value: object) -> None`

  Stores one JSON value under ``key``; no-op once the role is deleted. Only ``key`` changes: other values, including ones written meanwhile, are kept. Raises ``ValueError`` when ``key`` is one of the host's own initialization keys (such as ``self_seed``) or ``value`` is not JSON serializable.

## `shiori_sdk.core.proactive_host`

``PROACTIVE_HOST``: host services the proactive loop needs (P6b, #907). The port is process-wide. ## `shiori_sdk.core.sessions`

The ``sessions`` socket: roll back the latest passive turn, and presence (D10, D19). The core session module provides ``SESSIONS``. A turn's ``turn_id`` is the anchor user message id of that turn — the id memory ``source_ref`` values use — not a desktop ``metadata.turn_id``. ``last_passive_turn`` reads the turn without deleting it, so memory can roll back first over every message id of the turn. ``rollback_last_turn`` then deletes it under the session write lock; ``expected_turn`` makes it refuse when the latest turn is no longer exactly that turn (same anchor and same message ids) by then. The two calls are not one transaction. This ``Key`` (name ``sessions``) is unrelated to session metadata and media. That surface is ``SESSION_STORE`` (name ``session_store``) in ``shiori_sdk.core.services``. A plugin that rolls a turn back injects ``sessions``; one that reads metadata or media injects ``session_store``.

### `sessions`

Target `shiori_sdk.core.sessions.Sessions`.

#### `shiori_sdk.core.sessions.Sessions`

Read or delete the latest committed passive turn of one session.

- `last_passive_turn(session_key: str) -> core.sessions.PassiveTurn | None`

  The latest passive turn, or None when there is nothing to undo. Does not delete and does not take the session write lock.

- `async rollback_last_turn(session_key: str, *, expected_turn: core.sessions.PassiveTurn | None = None, rollback_source_ids: Sequence[str] = ()) -> core.sessions.RollbackResult | core.sessions.TurnChanged | None`

  Delete the latest passive turn, or None when there is nothing to undo. With ``expected_turn``, the turn is deleted only when both its anchor and its message ids equal it; otherwise nothing is deleted and ``TurnChanged`` is returned. ``rollback_source_ids`` are message ids whose memories were already rolled back; they pull the consolidation cursor back to the start of that window. Without them the cursor only rewinds for the deleted messages.

- `presence: core.sessions.Presence`

  Heartbeats for user messages and initiated sends (D19).

#### `shiori_sdk.core.sessions.PassiveTurn`

The latest committed passive turn of one session, read before deleting. ``message_ids`` are every message the rollback would delete: context frames, the anchor user message, tool messages and the whole assistant reply sequence. ``turn_id`` is among them.

- `turn_id: str`
- `message_ids: tuple[str, ...]`

#### `shiori_sdk.core.sessions.Presence`

User and initiated-send heartbeats, kept per session; the latest user message across all sessions can also be read. The stored columns stay ``last_user_at`` and ``last_proactive_at``. ``record_initiated_sent`` writes ``last_proactive_at``. A ``role:`` key is used as-is; any other key follows ``metadata.role_id`` when that session has one. This is the 4.0 baseline. 4.x cannot add methods here later.

- `record_user_message(session_key: str, when: datetime.datetime) -> None`

  Record that the user spoke in ``session_key`` at ``when``.

- `last_user_at(session_key: str) -> datetime.datetime | None`

  When the user last spoke, or None if this session has no record.

- `record_initiated_sent(session_key: str, when: datetime.datetime) -> None`

  Record that an initiated reply was sent for ``session_key`` at ``when``.

- `last_initiated_at(session_key: str) -> datetime.datetime | None`

  When an initiated reply was last sent, or None.

- `most_recent_user_at() -> datetime.datetime | None`

  When the user last spoke in any session, or None if never.

#### `shiori_sdk.core.sessions.RollbackResult`

The passive turn a session rollback deleted, and how the cursor moved.

- `turn_id: str`
- `deleted_ids: tuple[str, ...]`
- `last_consolidated_before: int`
- `last_consolidated_after: int`

#### `shiori_sdk.core.sessions.TurnChanged`

Nothing was deleted: the latest passive turn is not ``expected_turn``. ``turn_id`` is the anchor of the latest passive turn under the lock. It can equal the expected anchor when the turn's messages changed, such as a reply sequence that grew after ``last_passive_turn`` was read; otherwise a newer passive turn was committed in between.

- `turn_id: str`

## `shiori_sdk.core.tools`

Tool call events of the core tools module (#902). ``ToolCalling`` runs before a tool executes: ``on`` handlers may rewrite the arguments or reject the call with ``Veto`` (``ToolVeto`` to also close the tool loop). It fails closed: a handler error rejects the call. After the chain the core runs its fixed checks on the final arguments (its minimal shell guard, and the tool limits of an external-context turn), so no handler can rewrite a call past them. ``ToolCalled`` follows every call that ran or was rejected and may rewrite the result. Both are frozen projections of the host's call: ``arguments`` (and each ``tool_batch`` entry) is frozen into a read-only mapping on construction, so a handler may build its replacement with a plain dict, e.g. ``replace(event, arguments={**event.arguments, ...})``.

#### `shiori_sdk.core.tools.ToolCalled`

A tool call ended with ``status``; ``arguments`` are the final ones. ``result`` is the tool's output as text (the text part of a structured ``ToolResult``), or the rejection or error text. It cannot be vetoed: a veto fails the loop that made the call. Writable: ``result``. Only a changed ``result`` reaches the model, and then as plain text: rewriting the result of a tool that returned a structured or media ``ToolResult`` replaces it whole, dropping its media and structured content. Left unchanged, the tool's own result passes as it is.

- `session_key: str`
- `channel: str`
- `chat_id: str`
- `source: ToolSource`
- `call_id: str`
- `tool_name: str`
- `arguments: Mapping[str, object]`
- `status: ToolStatus`
- `result: str`

#### `shiori_sdk.core.tools.ToolCalling`

A tool is about to run with ``arguments``. ``tool_batch`` holds every call of the same model response as ``{"name", "arguments"}`` mappings and ``tool_batch_index`` this call's position in it. A passive turn also emits it for a call to a tool not loaded yet (still behind ``tool_search``): the tool never runs, only a finalizing ``ToolVeto`` takes effect there, and no ``ToolCalled`` follows. Writable: ``arguments``.

- `session_key: str`
- `channel: str`
- `chat_id: str`
- `source: ToolSource`
- `call_id: str`
- `tool_name: str`
- `arguments: Mapping[str, object]`
- `tool_batch: tuple[Mapping[str, object], ...]`
- `tool_batch_index: int`

#### `shiori_sdk.core.tools.ToolVeto`

Rejects a tool call with ``reason`` as its result. ``finalize`` also skips the rest of the batch and closes the turn with a summary instead of another model step.

- `reason: str`
- `finalize: bool`
