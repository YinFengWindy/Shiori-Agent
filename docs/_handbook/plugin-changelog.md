# 插件变更

SDK 源版本是 `packages/sdk/python/shiori_sdk/_version.py`。大版本是破坏性变更。这里只记已经定版的变更，不设 Unreleased 批次。

## 4.0.0

- P6b-6（#907）：主动说明从核心提示词移到 proactive 的 `PromptRendering` 贡献，按当前角色给出 `roles/<id>/PROACTIVE_CONTEXT.md`；插件停用后不再注入。宿主 presence 收口到 `SessionManager.presence`，SDK `SESSIONS.presence` 不变。保留 `SCENE_HOST.on_published`：它等后台接手，时机晚于进程资源发布，见[评估](../decisions/2026-11-02-p6b-publication-and-cleanup.md)。


- **breaking**（P6b-5，#907）：主动角色设置面板归 `plugins/proactive/ui`，通过 `roleSettings` 的 `storage: "plugin"` 挂载；核心 `roles.update` 拒绝 `proactive` 字段，前端 SDK 删除 `RoleProactiveConfig` / `RoleProactiveCandidate` 和角色响应中的该字段。插件投影进入 `plugin_state`，`plugin.proactive.settings_set` 通过 `ROLES.plugin_settings` 写原角色 JSON 的同一字段；核心不再解释其配置内容。
- `roleSettings` 新增可选 `save(roleId, values, previous, client)` 与 props `devMode`。RPC 保存发生在核心保存之后，失败保留插件草稿、更新核心基线并提示部分成功；原有无 `save` 贡献的原子扩展事务不变。主动 RPC 只合并已编辑字段并保留最新 overrides 等未编辑内容；禁用插件后面板消失、数据保留。


尚未发布到 npm / PyPI。桌面要等插件系统重构做完才带这个 SDK 出包。

- manifest 只接受 `api: 4`，并要求 `sdk` 最低约束。基线是 `>=4.0.0`。
- 删除 `runtime_api`。SDK 版本就是唯一版本号。
- `SESSIONS.presence`、`ROLES.plugin_settings`、`CONVERSATION.deliver_initiated_reply` 和 `InitiatedMessageCommitted` 进入 4.0 基线。`ROLES.plugin_settings` 写入 `proactive` 时清空已退役的 `candidates`，与桌面保存角色一致。
- `SESSIONS.presence` 新增 `most_recent_user_at()`：所有会话里用户最近一次发言的时间（#907 P6b-1a，主动循环的传感器用它）。宿主旧的 `proactive_v2` 心跳存储删除，核心与主动循环都改用 `SESSIONS.presence`，存储列不变。
- `CONVERSATION` 由宿主按代提供。`deliver_initiated_reply(reply: InitiatedReply) -> InitiatedDelivery`：`InitiatedDelivery` 是 `message_ids`（已提交的消息 id，按顺序）与 `complete`（整条回复都发出并落库）。`complete=False` 不是错误：单条回复被传输层拒绝（桌面没有接纳）时返回空 id，什么都不落库；序列被该聊天里的用户新消息、角色删除或关掉自然聊天打断时返回已发出并落库的前缀（可能为空），其余丢弃。投递角色由 `session_key` 决定，只接受规范的 `role:<role_id>`（带空格等非规范 key 抛 `ValueError`），目标必须是该角色能到达的（自己的桌面，别的角色的桌面在打开会话前就抛 `ValueError`，单条和序列都什么都不写、连序列的工具事实也不落库；经自己在线账号到达的绑定用户私聊，或经自己账号发出的 `account_target`）。`InitiatedReply` 带 `session_key`、`content`、`source`、`channel`、`chat_id`、`mood`、`thought`、`expected_mood_updated_at`、`moods`，以及可选的 `media`、`messages`、`account_channel` + `account_target`（SDK 的 `AccountTarget`，两者同时给或都不给）、`tool_facts`。`expected_mood_updated_at` 与 `moods` 取自工作开始时的 `CONVERSATION.reply_state`：心情按 `moods` 校验；之后被动回复已经写入更新的心情时，单条回复抛 `ValueError`，不发送、不落库、不覆盖心情；序列照常发出并落库，但不覆盖更新的心情（与现有自然回复一致）。`messages` 非空时 `content` 必须等于这些文本以空行拼接的结果，并且角色开启了自然聊天；否则分别抛 `ValueError`、`RuntimeError`。媒体挂在第一条上。`tool_facts` 只能跟着这段序列，否则抛 `ValueError`。序列投递需要运行时租约或已经绑定的渠道序列所有者。非角色会话、角色不存在、桌面目标不属于该角色、形状错误都在打开会话前抛错；心情校验失败在发送前抛错。发送失败或中途被拒会抛错：单条回复不落库；序列已发出的前缀保留落库并已发事件，桌面序列第一条就被拒时抛错而不是返回空结果；账号发送失败或结果未知的消息作为 `delivery_status=failed` / `uncertain` 的投递记录留在会话里，不进对话历史。落库的消息一律标 `proactive`、来源 `proactive`、`tools_used=["message_push"]`，不写 evidence item id；`source` 只进 `InitiatedMessageCommitted`。 部分回复已经落库之后，调用方任务被取消也不会丢掉结果：返回已落库的部分，取消在调用方下一次 `await` 时再抛出；还没有任何落库时取消直接传出。整条回复都已落库后抛出的任何异常（宿主自己的收尾：presence、好感记账、重新取得角色闸门、最终心情写入、提交事件）都只记日志，结果仍是 `complete=True`，期间收到的取消仍在调用方下一次 `await` 时抛出；其余异常都表示回复没有完整落库。`reply_state(role_id) -> RoleReplyState`（`moods`、`mood_updated_at`）读该代角色会话的心情目录和已存心情时间，角色不存在抛 `ValueError`；调用方在工作开始时把这两个字段抄进 `InitiatedReply`。
